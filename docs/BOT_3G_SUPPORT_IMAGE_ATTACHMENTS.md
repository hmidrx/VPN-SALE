# BOT-3G — private support image attachments

## Goal

Allow a customer to attach a screenshot or other image to an existing durable support ticket from the native Telegram bot, while keeping support media private, bounded, sanitized, permission-gated and attached to the existing Milestone 5-E support message history.

## Scope

- customer images only in this increment: JPEG, PNG and WebP
- maximum raw upload size defaults to 5 MiB
- maximum 20 attachments per support conversation by default
- every accepted image creates one durable `CUSTOMER_ATTACHMENT` support message and one existing-schema `support_attachments` row
- Admin Web can list attachment metadata and download the binary only through the authenticated support runtime
- no storage path, private root, customer id, Telegram id or file hash is returned to the browser or bot
- generic documents, PDFs, archives and executables remain unsupported until a malware/content-scanning pipeline exists

## Storage safety

The API does not persist the Telegram payload as received. It verifies the declared image type against the decoded image, rejects multi-frame or oversized images, enforces dimension and pixel bounds, converts to RGB, re-encodes the image and stores only the sanitized bytes. This strips EXIF/text metadata and normalizes active or malformed image content.

The local private support root is created with mode `0700`; each attachment file is created exclusively with mode `0600` under an opaque `SAT-...` asset reference. The user-facing normalized filename is generated by the platform and is not derived from Telegram input.

## Durable semantics

The upload path locks the owned support conversation before mutation. The idempotency scope is ticket-bound and the stored resource anchor binds the key to the content type plus raw payload digest. Replaying the same key and payload returns the existing attachment; reusing the key with different bytes is rejected with an idempotency conflict.

The attachment message uses the same sequence space and customer lifecycle rules as text replies. In particular, an attachment can resume a ticket that was waiting for the customer or reopen a resolved/closed ticket, then move it to `WAITING_FOR_SUPPORT` where the existing state machine permits that transition.

## Telegram UX

The newest ticket view exposes `📎 ارسال تصویر`. Selecting it stores only a short-lived expected-input marker and the idempotency key in the existing conversation state. The image bytes are downloaded from Telegram only after the bot verifies that a support attachment is currently expected. If no support attachment is expected, the existing manual-card-topup receipt flow remains authoritative.

## Admin UX

Attachment metadata is fetched separately from paged message history and keyed by durable message sequence. This avoids changing or weakening the signed cursor contract. Binary retrieval requires `support.attachments.read` and returns `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, a restrictive CSP and `Content-Disposition: attachment`.

## Schema and migration

No database migration is required. BOT-3G uses the existing `support_attachments` table and existing `support.attachments.read` / `support.attachments.manage` permissions from Milestone 5-E. Alembic head remains `0041_support_sla_escalations`.

## Deferred

Agent-to-customer image sending, generic document attachments, antivirus scanning, external object-storage adapters, retention/deletion workflows and inline Telegram re-delivery of historical support media are intentionally deferred to later increments.
